# 設計案: 骨格推定をスマホのブラウザの中で行う

作成: 2026-10-30 / 状態: 検討中（未着手）

## 1. 目的と前提

- 目的: レッスン中にスマホで撮ってその場で比較できるようにし、将来はサービスとしてインターネットに公開できる形にする
- 条件: 速いこと。サーバー費用はほぼ 0（無料枠が小さくてもよい）。利用者が増えても費用が増えにくいこと
- 前提: 先生の 1 台のスマホで操作する。1動画モード（先生と生徒を一緒に撮る）と 2動画モード（手本を 1 回撮り、生徒を順番に撮る）の両方を使う

## 2. 方針: 全部をブラウザの中で行う（サーバーは静的なファイル置き場だけ）

```
スマホのブラウザ
 ├─ 撮影・動画の選択（<input type=file accept=video/* capture>）
 ├─ ① 骨格推定  ……… ONNX Runtime Web（WebGPU、無ければ WASM）で姿勢推定モデルを動かす
 ├─ ② 人物の追跡 ……… ByteTrack 相当（簡易版）→ 人物をタップで選ぶ（B-1）
 ├─ ③ 解析     ……… Pyodide（ブラウザで動く Python）で今の dance_compare/core をそのまま動かす
 ├─ ④ 結果の表示 ……… 2 本の動画を同期再生し、骨格と印を canvas で重ねる（動画の書き出しはしない）
 └─ 保存       ……… 手本の動画と骨格データは端末内（IndexedDB / OPFS）
静的ホスティング（Cloudflare Pages など。無料・帯域無制限）
 └─ HTML / JS / モデル（約 10MB）/ Pyodide（約 15MB, 初回だけ読み込み、以後はキャッシュ）
```

この形の良いところ:
- **サーバー費用がほぼ 0**。利用者が増えても、配るのは静的なファイルだけ
- **動画が端末から出ない**。生徒が映った動画を外部に上げないので、プライバシーの説明がしやすい（サービスとしての強み）
- **今の解析ロジックを書き直さなくてよい**。`dance_compare/core`（約 2,700 行）は numpy と標準ライブラリだけで書いてあり、Pyodide でそのまま動く
- 画面を Streamlit の制約なしで作れるので、B-1（タップで人物を選ぶ）、B-3（トリミング）、B-4（撮影）をスマホ向けにきれいに作れる

あきらめる・変わること:
- 比較動画のファイル（comparison.mp4）は作らない。画面上で同期再生して見せる（共有用の書き出しは後で、7 の「後回し」を参照）
- Gemini での言語化は API キーを隠すために小さなサーバー（Cloudflare Workers の無料枠）が必要。ルールベースの文章は端末だけで動く

### 比べた別案

| 案 | 内容 | 良い点 | 問題 |
|---|---|---|---|
| **A. 全部ブラウザ（本案）** | 上の図 | 費用 0・速い・動画が出ない | 作り直す部分が多い |
| B. 骨格推定だけブラウザ | 骨格データだけをサーバー（Streamlit）に送って解析 | 画面は今のまま | 比較動画を作るには結局動画を上げる必要がある。Streamlit のホスティング（常時起動）が必要 |
| C. サーバーの GPU（Modal） | 今のアプリをほぼそのまま載せる | 作業が少ない（3〜5 人日） | 使った分の費用がかかる。動画を外部に上げる |

## 3. 各部分の設計

### ① 骨格推定（いちばん難しい）

- 実行環境: ONNX Runtime Web。WebGPU（iOS 26 以降の Safari、Android Chrome）で動かし、使えない端末は WASM（遅い）
- モデルの候補（PoC で速さと精度を比べて決める）:

| モデル | 複数人 | ライセンス | 備考 |
|---|---|---|---|
| YOLO11n-pose（今と同じ） | ○ | **AGPL-3.0** | 今と同じ結果になる。ただし公開サービスで使うとソースの公開義務、または Ultralytics の有料ライセンスが必要 |
| RTMO-s（MMPose） | ○ | Apache-2.0 | 1 段で複数人。精度は YOLO11 と同程度と言われる。商用で使いやすい |
| MediaPipe Pose Landmarker | ○（人数指定） | Apache-2.0 | スマホでとても速い。追跡 ID が無く、複数人だと精度が落ちやすい |
| MoveNet MultiPose | ○（6 人まで） | Apache-2.0 | 簡単な追跡つき。精度は低め |

  → **サービスとして公開するなら、AGPL の YOLO から Apache の RTMO などに替えるのが無難**（これはサーバーで動かす案でも同じ問題）
- コマの取り出し: `<video>` を等倍〜2 倍速で再生し、`requestVideoFrameCallback` で 1 コマずつ 640px の canvas に描いて推定する。
  推定が追いつかないときは再生を止めて待つ。iPhone の 4K・HEVC も Safari が自前で再生するので変換は不要
- コマ数: 今と同じ 30fps を目標。遅い端末では 15fps に落とし、解析側で補間する
- 画面を消さない: Screen Wake Lock API（Safari 16.4 以降）で推定中に画面が消えて止まるのを防ぐ
- 出力: 今の `TrackSet` と同じ形（ID ごとの 17 点の座標・信頼度・枠）→ JSON / バイナリで Pyodide に渡す

速さの見込み（1 分の動画・30fps = 1,800 コマ。PoC で要確認）:

| 環境 | 1 コマ | 1 分の動画 |
|---|---|---|
| WebGPU（iPhone 15 以降・最近の Android） | 20〜40ms | 約 40〜70 秒 |
| WASM（WebGPU の無い端末） | 100〜250ms | 3〜7 分（15fps に落として半分） |
| 参考: 今の Mac（GPU） | — | 実測待ち |

### ② 人物の追跡と選択

- 追跡: ByteTrack の簡易版（枠の重なり + 動きの予測で ID を付ける）を Python（numpy）で書き、Pyodide で動かす。
  ID のつなぎ直し（`pose/tracking.py` の stitch / select_pair）はそのまま使える
- 人物の選択: 動画を止めた画面で人物をタップ（B-1 の設問形式「お手本の人は？」→ タップ、「比べる人は？」→ タップ）

### ③ 解析（Pyodide）

- `dance_compare/core`・`feedback`・`pose/tracking.py`・音声同期の計算部分をそのまま使う
- 動画ファイルや ffmpeg を使う部分（`media/video.py`, `media/proxy.py`, `render/`）はブラウザでは使わないので、入口だけ作り直す:
  - 骨格: ① の結果を `TrackSet` に変換
  - 音声（2動画モードの同期）: ブラウザの Web Audio API で音声を取り出し、numpy の配列として `media/audio.py` の計算に渡す（librosa は使わない）
- 読み込み時間: Pyodide + numpy で約 15MB。初回は数秒〜十数秒、2 回目からはキャッシュで速い。骨格推定の間に裏で読み込めば待ち時間は見えない

### ④ 結果の表示

- 2 本の動画（1動画モードなら同じ動画を 2 つの枠で切り出し）を、時間の対応表に合わせて同期再生し、骨格と赤い印を canvas で重ねる
- 直すところ: その区間を 0.5 倍速でループ再生（今の短い動画と同じ見せ方。ファイルは作らない）
- スコア・全体の傾向・詳細は今と同じ内容

### 保存

- 手本の動画と骨格データを端末内に保存（IndexedDB / OPFS）。2動画モードで手本の骨格推定をやり直さなくてよい
- 端末の保存容量の上限に注意（Safari は空き容量に応じて制限。長い 4K 動画は大きい）

## 4. 作業の段階と工数の見積もり

人日 = 開発者 1 人が 1 日で進める量の目安。実装は私（Claude）が行う前提で、実際の日数は
「iPhone 実機で試してもらう → 直す」の往復回数に大きく左右される。

| 段階 | 内容 | 工数 | 難易度 |
|---|---|---|---|
| 0. PoC（危険の確認） | iPhone のブラウザで ①の速さと精度（検証セットで今の YOLO と比較）、③ Pyodide で core が動くか | 3〜5 人日 | ★★★★ |
| 1. 骨格推定 | モデルの変換・読み込み、コマの取り出し、推定、後処理（NMS・座標変換・回転）、進み具合の表示・中止、画面を消さない | 5〜8 人日 | ★★★★ |
| 2. 追跡・人物の選択 | 簡易 ByteTrack、つなぎ直しの組み込み、タップで選ぶ画面 | 4〜6 人日 | ★★★ |
| 3. 解析の組み込み | Pyodide での実行、TrackSet への変換、音声同期（Web Audio）、比較する区間の自動推定 | 3〜5 人日 | ★★★ |
| 4. 結果の画面 | 同期再生 + 骨格の重ね描き、直すところのスロー再生、スコア・傾向・詳細 | 6〜9 人日 | ★★★ |
| 5. アプリの骨組み | 撮影・選択、トリミング（今の部品を流用）、手本の保存、設定、ホーム画面に追加（PWA）、モデル等のキャッシュ | 5〜8 人日 | ★★ |
| 6. 仕上げ | 今の Python 版と結果が合うかの確認（検証セット）、しきい値の再調整、iPhone / Android 実機での調整、公開（Cloudflare Pages + 自動デプロイ） | 4〜6 人日 | ★★★ |
| **合計** | | **30〜47 人日** | |

- 期間の目安: 開発者 1 人なら 1.5〜2.5 か月。私が実装する場合は作業自体は速いが、実機確認の往復が律速になるので、
  週に数回試してもらえるなら **3〜6 週間** 程度
- **段階 0 だけ先にやれば、残りの見積もりの幅がかなり狭まる**（いちばん不確かなのは ① の速さ）

難易度の目安: ★★ = 定番の作り方がある / ★★★ = 工夫が要るが見通しは立つ / ★★★★ = 端末ごとの差や未知の問題が出やすい

## 5. 主な危険と対策

| 危険 | 影響 | 対策 |
|---|---|---|
| WebGPU の無い iPhone（iOS 26 より前）で遅い | 1 分の動画に数分 | 15fps に落とす、軽いモデル、推定中も途中経過を見せる。対象端末を決める |
| Safari のメモリ上限 | 長い動画・4K で落ちる | 1 コマずつ 640px に縮小して処理し、画像を溜めない |
| モデルを替えると結果が変わる | しきい値の調整のやり直し | 段階 0 で検証セット（validation/）を使って今の YOLO と比べる |
| ライセンス（YOLO は AGPL） | 公開サービスで問題 | Apache のモデル（RTMO・MediaPipe）を第一候補にする |
| 推定中に画面が消える・別のアプリに切り替える | 推定が止まる | Wake Lock。途中から再開できるようにする |
| 初回の読み込みが重い（約 25MB） | 最初だけ待つ | キャッシュ（Service Worker）。骨格推定中に裏で読み込む |

## 6. 今の Python 版の扱い

- Python 版（Streamlit）は、精度の検証・しきい値の調整・新しい評価項目の試作用として残す
- 解析の中身（core）は両方で共有するので、Python 版で調整した結果がそのままブラウザ版にも反映される

## 7. 後回しにするもの

- 3D 推定、ゴルフモード（E-1）
