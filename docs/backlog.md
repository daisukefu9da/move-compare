## A. 処理の速さ

### A-1. 骨格推定が遅い【最優先】
- フィードバック: 人物検出の骨格推定に約 3 分かかる（1分43秒の動画）。このままでは使い物にならない
- 見立て: 全フレームを CPU で処理している。iPhone の動画は 60fps・4K が多く、1分43秒で約 6,000 コマを 4K のまま読んでいる
- 対策案:
  - Mac の GPU を使う（Apple シリコンなら `device="mps"`）
  - 解析に必要なコマだけ処理する（60fps → 15〜30fps に間引く）
  - 推定前に縮小する（推定は 640px で行っているので、4K のまま扱う必要はない）
- 規模: 小
- 対応済み（第一段階, 2026-10-21）:
  - 分析用の軽い動画（長辺 960px・30fps, `.cache/proxy/`）を ffmpeg で作り、骨格推定はそれで行う。
    座標は元の動画の解像度に戻して保存し、比較動画は元の動画から作る（方針: 分析用だけ画質を落とし、
    ユーザーの目に触れる動画の画質は変えない）
  - GPU があれば自動で使う（Apple シリコンは mps, NVIDIA は cuda。失敗したら CPU。環境変数 DANCE_COMPARE_DEVICE で指定可）
  - 比較動画の映像も分析用の軽い動画から作る（各画面は高さ 480px に縮小するので見た目は変わらない）。
    720px に上げたら書き出しが重くなったため 480px に戻した（フィードバック: 以前と同じくらいの方が良い）。
    10 秒の 4K・60fps 動画で比較動画の書き出し 28.8 秒（720px・元動画から）→ 8.4 秒
  - 計測（クラウドの CPU 4 コア, 10 秒の 4K・60fps 動画）: 41 秒 → 17 秒（軽い動画の作成 2.4 秒 + 推定 約 14 秒）
- 残り: 実機（Mac）での速度の確認。まだ遅ければ、推定の解像度・フレームの間引きを強める、CoreML への変換などを検討

## B. 操作のしやすさ（画面）

### B-1. 人物をタップ／クリックで選ぶ
- フィードバック: ID 番号での指定は分かりづらく、直感的でない。本格的なアプリなら
  「お手本の人は？」→ タップ、「お手本と比較する人は？」→ タップ、と設問に対して操作する形が適切
- 方針: 賛成。設問形式でタップ選択にする（Streamlit でも作れる）

### B-2. 「人物を選ぶフレーム番号」が分かりづらい
- フィードバック: 対象のフレームを指定して、そこで検出できる人物を選ぶ、という仕組みが分かりづらい
- 対応済み（一部）: 秒のスライダーに変更し、各 ID が映っている時間帯を表示するようにした
- 方針: B-1 の設問形式に置き換えて、意識しなくてよい形にする

### B-3. 比較する区間を動画を見ながら選ぶ
- フィードバック: 秒数の指定は分かりづらい。iPhone の動画のトリミングのように、コマ送りで見ながら操作したい
- 方針: 今の Streamlit では作りにくい。「決めたいこと 1」とあわせて検討

### B-4. その場で撮影してアップロードして比較する【必須】
- 当面の方法: PC で起動したアプリに、スマホから同じ Wi-Fi でアクセスすれば「撮影 → アップロード」ができる
  （Streamlit 起動時に表示される Network URL を開く）
- 方針: 本格対応は「決めたいこと 1」とあわせて検討

## C. 評価とフィードバックの見せ方

### C-1. 指摘を上位 3 つの瞬間に絞り、静止画で見せる【対応済み】
- フィードバック: フィードバックが多すぎてしんどい
  - 全部を見せず、ズレの大きい瞬間を上位 3 つくらいに絞る
  - その瞬間の静止画をお手本と自分で並べて見せ、体の部位に印をつける
- 方針: 賛成。アプリの価値の中心になる。全指摘の一覧は「詳細」として残す（精度検証用）
- 対応済み（2026-10-23）:
  - 区間ごとに「一番大きい指摘 + 残りの 1/4」（部位の重み込み）で点数を付け、隣り合わない区間から上位 3 つを選ぶ
  - 一番大きい指摘がすでに見せた内容と同じ区間は選ばない（毎エイト同じ癖が出る場合は 1 か所だけ見せ、「同じズレが他に何か所」を添える）
  - 瞬間 = その区間で一番大きい指摘のズレが最大のコマ。お手本と自分の静止画を人物の周りで切り出して並べ、ズレている部位に赤い丸
    （moment_1.jpg など）。画面では「直すところ」として表示し、全指摘・時系列は「詳細」に移した
  - フィードバック（2026-10-24）: 直すところは比較動画の下に。画像が大きすぎるので、左に画像・右に修正点の 2 カラムに。
    静止画だと前後のつながりが分からないので、前後を切り出した短い動画に
  - 対応済み（2026-10-24）: 比較動画の下に移動、2 カラム表示。瞬間の前後 1.5 秒を 0.5 倍速のスローの短い動画
    （moment_1.mp4 など, 自動ループ・音声なし）にした。印はズレの大きいコマの前後 0.35 秒だけ表示。
    人物の切り出し範囲は短い動画全体で固定（画面が揺れない）。静止画は report.md 用に残す

### C-2. 「拍とのズレ」の位置づけ【決定: 廃止・対応済み】
- フィードバック: 手本にどれだけ近づけるかという観点ではやや異質で、評価を分かりづらくしている。
  必要ではあるので、「手本と音の取り方がどう違うか」などのアドバイスにまとめる方が納得感がありそう
- 方針: 評価軸（スコア）から外し、手本との音の取り方の違いとしてアドバイスにまとめる
- 関連: 大きな評価軸（例:「ミュージカリティ・リズム」）の中に細かい項目を並べる構成も検討（会話中の案）
- 決定（2026-10-23）: リズム評価は廃止。遅れ・走りは「手本とのタイミング」で評価する
  - 理由: 部分的に遅れていてもリズムは高得点になった（拍とのズレの平均・ばらつきで手本と比べるため、部分的な遅れが
    平均で埋もれる）。拍の検出精度も不安定（76 BPM と検出され、手本自身も拍に合う割合が 25%）
  - 対応済み: スコア・指摘・画面（スライダー）から外した。数値は report.json の rhythm に参考として残す

### C-3. 「レベル・向き」を「身体の形」に統合【対応済み】
- 方針: 賛成
- 対応済み（2026-10-23）: 観点を「身体の形／動きの大きさ／キレ／タイミング」の 4 つに整理。レベル・向き・足幅・頭は身体の形、
  移動量は動きの大きさ、着地はタイミングへ。スコアは観点ではなく部位（C-5）ごとに出す

### C-5. 部位ごとの重み付け（新規, 2026-10-23）【対応済み】
- フィードバック: 足・腰・首・頭は大事だが、腕はジャンルで評価が変わる（ロックは重要、House は違うのが味になることも）。
  スコアリングを部位ごとに重み付けしたい
- 決定: ジャンルのプリセットは作らない（重みはユーザーが調整）
- 設計案（未確定）:
  - 評価を部位でまとめ直す: 足（膝・股関節の角度、足首の振れ幅・キレ、足幅、着地）／腰・体幹（沈み込み、傾き、向き、重心移動）／
    首・頭（頭の向き・傾き。新規に測定を追加）／腕（肘・肩の角度、手首の振れ幅・キレ）。タイミングは全身として別枠
  - 総合スコア = 部位スコアの重み付き平均 + タイミング。重みは指摘の優先度（上位 3 つの選定）にも掛ける。重み 0 = 評価しない
- 決定: 部位は 足／腰（体幹）／頭（首の動きを含む）／腕 ＋ タイミング（全身）。首と頭は骨格の点（鼻・目・耳のみ、首・顎の点が無い）
  では区別できないので 1 つにまとめる
- 対応済み（2026-10-23）:
  - 頭の測定を追加: 傾き（両耳の線と両肩の線の角度）、顔の向き（両耳の間の鼻の位置）、横スライド・上下（各自の普段の位置からの差）。
    顔の点の信頼度が低いコマ・背中向きは評価しない
  - 部位ごとのスコア、重み付きの総合スコア。重みは指摘の優先度（直すところの選び方）にも掛ける。重み 0 = 評価しない
  - 画面のサイドバーに「部位の重み」（0〜3）、高度な設定に頭のしきい値

### C-4. 判定が厳しすぎる
- フィードバック: 身体の形・動きの大きさがかなり低スコアになった
- 原因の候補（実データで確認が必要）:
  - 二人の立ち位置・カメラとの角度の違いによる 2D 骨格のズレ
  - しきい値（関節角度 20° など）
  - スコアの計算式（差がスケール値のとき約 37 点になる指数関数）
- 必要なもの: 「決めたいこと 3」のデータ
- 実データ（report_1.md, 1動画モード・横並びで本人が少し後ろ）で分かったこと:
  - 身体の形 52 点なのに指摘 0 件 → スコアが 1 コマごとの角度の差（骨格推定のぶれ約 20°）の平均で計算されていた
  - リズム 48 点なのに拍とのズレは本人 +18ms／手本 +17ms とほぼ同じ → ばらつきを手本と比べずに減点していた
  - 腰の位置が常に「手本より低い」（本人の感覚では少し高め）→ 足首〜腰の高さを胴の長さ比でそのまま比べていたため、
    体型（脚と胴の比率）の違いが出ていた
  - サイドバーで「緩める」つもりで「動きが小さいとみなす比率」を 0.95 にして、逆に厳しくなっていた（向きが逆の項目）
  - サイドバーのしきい値がスコアに反映されていなかった
- 対応済み（2026-10-21）:
  - スコアをしきい値と連動（区間ごとのズレがしきい値の何倍か → 半分以下 100 / 1 倍 80 / 2 倍 50 / 3 倍 25 / 6 倍 0 点）
  - リズムのスコアは手本との差で評価
  - 腰の高さは各自の普段の高さ（中央値）からの沈み込みで比較。しきい値 0.12 → 0.15
  - スライダーをすべて「大きくするほど緩い」に統一（動きの大きさ・キレは「差 [%]」に言い換え）。基本 4 項目 +「高度な設定」に分けた
  - 設定項目名の変更: amplitude_ratio_low/high → amplitude_tolerance, sharpness_ratio_low → sharpness_tolerance（古い名前も読める）
- 未確認: 実データでの新しいスコアの妥当性（同じ動画で再解析して確認してもらう）

## E. 新しい用途の案

### E-1. ゴルフのスイング比較（2026-10-24, パーソナルコーチとの会話から）
- 状態: 案。ダンスの実データでの確認（C の妥当性）を優先し、その後に検討する
- そのまま使える: 人物の検出・2動画モード（プロ／コーチ／過去の自分との比較）、左利きは左右反転、関節角度の比較、
  部位の重み（頭・腰・膝を重く、腕を軽く など）、「直すところ」のスロー動画
- 作り直しが必要:
  - 時間の区切り: 拍・カウントの代わりにスイングの局面（アドレス、テークバック、トップ、切り返し、インパクト、フィニッシュ）。
    手首の動きから検出する
  - テンポ: バックスイングとダウンスイングの時間比（目安 3:1）
  - フレームレート: ダウンスイングは約 0.25 秒なので 60fps 以上（できれば 120〜240fps のスロー撮影）。
    今は分析用に 30fps に間引いているので変更が必要
  - 評価項目: 頭のブレ、背骨の前傾、腰のスライド、膝の曲げ、体重移動 など
- できないこと: クラブ・ボールは測れない（骨格は手首まで）。体の回転（肩と腰のねじれ差など）は 1 台のカメラの 2D 骨格では正確に測れない
  → 正面と後方の 2 方向を別々に比べるのが現実的。3D 推定（下記）は将来の選択肢
- 3D 推定: 2D の関節座標から奥行きも含めた 3D の姿勢を推定する技術（例: MediaPipe の world landmarks、2D→3D 持ち上げモデル
  （MotionBERT など）、複数カメラでの三角測量）。回転・前後の動きが測れるようになるが、1 台のカメラからの推定は誤差が大きい。
  ダンスの「腕を前に出しているか横か」「体のひねり」の評価にも効く
- 先に確認したいこと（コーチに）: プロとの比較か過去の自分との比較か／撮影は正面と後方の 2 方向か／一番知りたい項目
- 簡単な確認: 正面と後方から 60fps 以上で撮ったスイング動画 1〜2 本で、インパクト付近でも骨格が取れるかを見る
- 注意: プロの動画の転載は D-1 と同じく著作権の問題がある（コーチが撮った動画は問題ない）

## 対応済み（参考）

- アップロード上限を 4GB に引き上げ（Streamlit の既定 200MB で弾かれていた）
- 比較動画の書き出しが失敗しても解析結果を表示（iPhone の音声形式などで ffmpeg が失敗するケース）
- 1動画モード: 比較する区間の指定と自動推定（二人の動きの同期度）
- 1動画モード: 追跡が途切れたときのつなぎ直しを改善し、区間が短くなった場合は理由を表示
- 1動画モード: 人物を選ぶ時刻を秒で指定し、各 ID が映っている時間帯を表示
